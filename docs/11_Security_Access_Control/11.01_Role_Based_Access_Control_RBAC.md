# 11.01 Role-Based Access Control (Branch-Aware RBAC)

## Purpose

PickUrVeggie ERP V3 implements a Branch-Aware Role-Based Access Control (BA-RBAC) model.

The security system shall ensure that users only access the companies, branches, modules, and records they are explicitly authorized to access.

The system follows the principle of least privilege:

A user shall receive the minimum level of access required to perform their responsibilities.

---

# Security Hierarchy

The access hierarchy follows:

Company
│
├── Branch
│   │
│   ├── User
│   │   │
│   │   └── Role
│   │       │
│   │       └── Permissions

---

# Controlled Role Vocabulary (Stage A · ADR-001)

The roles named in this document are **default seed data, not a hard-coded enum.** The model must support custom, company-specific, and branch-specific roles. Two distinctions are mandatory:

- **System roles (RBAC)** — the access-control roles defined here and in `20.03` (data-driven rows in the `roles` table).
- **HR job titles** — descriptive positions (e.g. Manager, Accountant, Cashier, Harvester) defined in HR (`21`); these are **not** system roles and must be mapped to one or more system roles.

Authorization checks are **permission-based, never role-name-based** (no `if role == 'Admin'`). Use canonical spellings (e.g. `Administrator` not `Admin`; `Co-Owner` consistently). This resolves audit findings P2-03, P3-03, P4-05.

# Global Corporate Roles

Global roles have access across all branches.

## Developer

Highest technical authority.

Permissions:

- Full system access
- Architecture management
- Debugging tools
- Database administration
- Security configuration

---

## Owner

Business authority over the company.

Permissions:

- View all branches
- View all financial reports
- Manage users
- Create branches
- Assign management roles
- View consolidated dashboards

---

## Co-Owner

Permissions depend on owner configuration.

Possible access:

- All branches
- Financial reports
- Operations
- Management functions

---

## General Manager

Responsible for company-wide operations.

Permissions:

- View all branches
- Manage branch operations
- Review production reports
- Manage supervisors
- Monitor company performance

---

## Corporate Accountant

Financial authority across branches.

Permissions:

- View all branch financial records
- Create financial reports
- Generate consolidated financial statements

Restrictions:

- Cannot manage farm operations
- Cannot modify inventory unless specifically authorized
- Cannot manage employees unless granted permission

---

# Branch Roles

Branch roles are limited to assigned branches.

---

## Branch Supervisor

Permissions:

- Manage daily branch operations
- Manage workers
- Manage schedules
- Monitor inventory
- Record production
- View branch reports

Restrictions:

- Cannot access other branches

---

## Operator

Permissions:

- Perform assigned operational tasks
- Enter production data
- Update approved records

Restrictions:

- Limited administrative authority

---

## Worker

Permissions:

- View assigned tasks
- View schedules
- Submit work logs
- View personal payroll records if permitted

Restrictions:

- Cannot access branch management information
- Cannot view other employee records

---

# Multi-Branch User Roles

A single person may have different roles in different branches.

Example:

Juan Dela Cruz:

Siargao Branch:
- Branch Supervisor

Cebu Branch:
- Worker

Permissions are determined by:

- User identity
- Active company
- Active branch
- Assigned role
- Additional permission overrides

# Temporary and Special Permissions

The system shall support temporary access assignments.

Examples:

- An employee temporarily assigned to another branch
- An external auditor with limited access
- A consultant with a fixed expiration date

All temporary permissions shall include:

- Approval authority
- Start date
- Expiration date
- Audit records

---

# Security Enforcement

Access control shall be enforced at multiple levels.

## User Interface Layer

Users shall only see menus, buttons, and information they are authorized to access.

---

## API Layer

All requests shall validate:

- User identity
- Company access
- Branch access
- Role permissions

---

## Database Layer

Supabase Row-Level Security (RLS) shall be the final authority.

Even if a malicious user bypasses the interface, unauthorized database records shall not be returned.

---

# Audit and Compliance

Every permission change shall be recorded.

The audit record shall include:

- Who granted access
- Who received access
- Company
- Branch
- Role assigned
- Date and time
- Expiration date if temporary

---

# Architecture Rule

No module, API, database query, AI service, mobile application, or integration shall bypass Branch-Aware Role-Based Access Control.

Security rules must always consider:

- Company
- Branch
- Role
- Permission level

before allowing any action or displaying any information.
