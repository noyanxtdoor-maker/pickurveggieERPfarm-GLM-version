# 20.01 Database Philosophy

## Purpose

The PickUrVeggie ERP V3 database is designed as a multi-tenant, multi-branch, enterprise-grade PostgreSQL architecture powered by Supabase.

The database shall support:

- Multiple companies
- Multiple branches per company
- Thousands of users
- Millions of operational records
- Offline-first synchronization
- AI-assisted operations
- IoT device integrations

The database is the single source of truth for all business operations.

---

# Core Database Principles

## 1. Multi-Tenant Company Isolation

Multiple companies may operate within the same PickUrVeggie ERP V3 platform.

Each company must have complete logical separation of:

- Users
- Branches
- Financial records
- Inventory
- Agricultural records
- Documents
- AI insights

Every company-owned record shall contain:

- company_id

---

## 2. Multi-Branch Data Ownership

A company may operate multiple branches.

Operational records shall belong to a specific branch.

Examples:

- Inventory
- Production activities
- Employees
- Payroll
- Sales
- Expenses
- Equipment
- IoT sensors

Every operational record shall contain:

- branch_id

---

## 3. Database-Level Security

Security shall never depend only on the application interface.

Supabase Row Level Security (RLS) shall be the final authority controlling access.

All database queries shall verify:

- Company authorization
- Branch authorization
- User role
- Permission level

Unauthorized users shall receive no data.

---

## 4. Audit Metadata Standards

Every important business record shall maintain audit information.

Standard audit fields:

- created_by
- created_at
- updated_by
- updated_at

Additional audit logs shall record:

- Previous values
- New values
- Reason for change
- Approval references

---

## 5. No Hard Deletes

Critical business records shall never be permanently removed by normal users.

Records shall use lifecycle statuses such as:

- Active
- Inactive
- Archived
- Cancelled
- Void

Historical records must remain available for auditing and reporting.

---

## 6. Immutable Financial and Historical Transactions

Historical transactions shall never be modified or erased.

Examples:

Financial transactions:

Purchase → Inventory Asset

Consumption → Production Cost

Harvest → Finished Goods Inventory

Sale → Revenue + Cost of Goods Sold

Corrections shall be handled using:

- Adjustment entries
- Reversal entries
- Corrective transactions

The original transaction shall always remain in history.

---

## 7. Offline-First Synchronization

PickUrVeggie ERP V3 supports field operations with limited or no internet connectivity.

Data flow:

Device
↓
Local Database
↓
Synchronization Queue
↓
Supabase PostgreSQL

Offline records shall:

- Preserve original timestamps
- Preserve the creator identity
- Maintain branch ownership
- Resolve conflicts using defined synchronization rules

---

## 8. API, AI, and Integration Security

All system integrations shall follow the same security model.

This includes:

- Web applications
- Mobile applications
- AI assistants
- IoT devices
- External APIs

No integration shall bypass:

- Company isolation
- Branch isolation
- Role permissions
- Audit requirements

---

## 9. Database Scalability

The database shall support future growth including:

- Hundreds of companies
- Hundreds of branches per company
- Thousands of users
- Millions of records
- High-volume IoT sensor data

Database schemas must avoid assumptions that the system will only operate as a single farm.

---

# Database Constitution Rule

Every table, relationship, API, synchronization process, AI feature, and reporting engine developed for PickUrVeggie ERP V3 must comply with this database philosophy.

If a feature violates company isolation, branch isolation, security policies, audit requirements, or data integrity rules, the design shall be considered invalid.
