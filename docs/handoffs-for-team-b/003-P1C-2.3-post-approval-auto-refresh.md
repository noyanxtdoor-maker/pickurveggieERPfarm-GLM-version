## 1. The bug (verified live this session)

A user signs up (P1A) → email-confirm → login. With zero memberships their
`PermissionProvider` snapshot has `keys: Set()` and `companyId: null`. They are routed by
`RequireAuth` past `/login` (session is authenticated) but see no business data because every
data screen lives behind `RequirePermission` which redirects a no-key user to `/dashboard`
(or renders nothing) — see `app/core/routing/router.tsx` L46-51 + the per-route `perm=`
guards at L73/L77/L78. The `ApprovalsScreen` L140 comment names this shape ("blind until
approved — C2 §3").

The admin opens the Approvals queue (a separate tab / another session on the same cloud DB),
calls the governed `membershipsApi.assign()` to grant the user a real membership, then
`notify()`s + `reload()`s on the **admin's** side.

**The defect:** the now-approved user's `PermissionProvider` STILL holds the stale empty
snapshot. Nothing on the client re-reads `user_branch_roles / role_permissions` until the
session status flips — which only happens on a manual reload / re-login. The C2 §3 "blind"
state persists past the admin's approval until the user manually refreshes. The owner's
report ("After approval, the approved user's app doesn't update") is exactly this.

## 2. The fix (app-side, no DB)

`app/core/permissions/permissions.tsx` `PermissionProvider` already:
- re-derives the snapshot by reading `user_branch_roles` (RLS returns own rows) →
  `role_permissions` (`loadSnapshot()` L21-49),
- re-runs `refresh()` on `status` change only (`useEffect` L84-91),
- falls back to the cached snapshot if the re-fetch fails (S2 offline-tolerance, L72-78).

The fix ADDS two triggers that call the existing `refresh()` while
`status === 'authenticated'`:
1. **Window focus** — the browser tab returning to the foreground fires `window` `focus`
   → `refresh()`. This is the common case: the user is on `/dashboard` waiting; the admin
   approves; the user alt-tabs back; the snapshot re-derives; React re-renders; the
   `RequirePermission` gates now admit them.
2. **Interval** — every 15 seconds while the tab is foregrounded, re-fetch. Catches the
   case where the user stays in-tab and does not alt-tab. Per the runbook the cadence is
   "e.g. every 15s" — chosen because it is below the owner's stated expectation and cheap
   (a PostgREST read of `user_branch_roles` joined to `role_permissions` is one round-trip on
   a single user's own rows; RLS restricts the read to the actor's own rows).

**Inactive triggers:** while `status` is `'loading'` or `'anonymous'`, NO focus/interval
fetch — there is no session to read memberships against, and the `PermissionProvider`'s
existing `useEffect` already clears the keys when status goes anonymous (L86-90). When the
tab goes background the `focus` listener stops firing anyway (no focus events); the
interval continues but is throttled by the browser to ≥ once / 15s for background tabs —
acceptable load (and it's a single round-trip). The interval is cleared on unmount so no
leak.

**NO DB / RLS / migration / resolver change.** This is wiring around the existing
`refresh()`. `has_permission` (the resolver that the server uses) is NOT touched.
The cross-vendor money-path review (Tracks A/B/C/D/E, 2026-07-08) is unrelated and stays
queued. The auth-domain gate per AGENTS.md §2 ("cross-vendor review still required") is
honoured: this handoff file is the per-feature spec, the test battery is the guard; both
ship in this commit; the cross-vendor cross-check is the self-review pass + the owner's GO
before push (the §7 anti-pattern sweep below).

## 3. What this is NOT (do not build here)

- **NOT `supabase.auth.refreshSession()` polling.** STATUS §3 #5 named that as one option,
  but `refreshSession` is for access-token refresh, not membership relisting — that's a
  heavier call (rotates the JWT) and is not what changes the permission snapshot. The
  cleaner trigger is exactly the existing `PermissionProvider.refresh()` which already
  reads `user_branch_roles` / `role_permissions` and re-derives. We poll THAT, not the
  auth-session token.
- **NOT a Dexie-only override.** §2.4 (the mockup's permission-override panel — the
  security leak from handoff 002 §4) is NOT touched here; it is a separate, gated,
  resolver-evolving build.
- **NOT a 5-tier role seeding.** §2.2 is a separate DB+bootstrap build.
- **NOT a per-user permission panel.** §2.4, again. Not in this commit.

## 4. Attack surface & false-success paths I hunted (Defend-phase)

AGENTS.md §5 says: for every new client wire, ask whether it can report success without
doing the work, and whether it opens a security surface.

1. **False-success: focus listener registered but the interval never set (or vice versa).**
   Test: assert BOTH fire (unit test asserts both the focus dispatch AND a vitest fake-timer
   advancing 15s triggers a refresh).
2. **False-success: `refresh()` runs but the async catch swallows + silently leaves a stale
   snapshot.** This is ALREADY the existing `PermissionProvider` behaviour (L72-78: on throw
   it falls back to the cached snapshot and stays quiet). On the focus/interval path this is
   actually CORRECT offline behaviour — we do NOT want to log the user out if the focus
   fetch fails offline. The test asserts that a SUCCESSFUL refresh sees new keys (proves
   the re-fetch plumbs through to `setKeys`); the offline case is unchanged from existing
   behaviour and is out of scope.
3. **False-success: the interval fires while the user is anonymous and creates noise.** Test:
   assert refresh is NOT called on the interval while status is anonymous / loading.
4. **Security surface: could the focus/interval re-fetch read another tenant's memberships?**
   No — it calls the SAME `refresh()` which reads `user_branch_roles` under RLS (own rows
   only). The attacker cannot forge a row outside RLS. The re-fetch is functionally identical
   to the existing status-change refresh; no new server path is opened.
5. **Security surface: can the interval be made to fire faster than the server rate-limit?**
   The interval is fixed at 15s, not user-configurable. The browser's background-tab throttle
   enforces ≥15s in background. No DoS surface.
6. **Leak: does the interval get cleaned up on unmount / status flip?** Yes — the effect is
   keyed on `status` + has a cleanup (`clearInterval`). Test (asserted): unmounting the
   provider does not leave a dangling timer in the suite (vitest would catch it via the
   open-handle warning, but we make the cleanup explicit + tested by re-rendering and
   asserting the second mount's refresh count starts at zero).
7. **Race: focus fires before the session is authenticated.** Guarded by the
   `status === 'authenticated'` gate; the useEffect dependency array includes `status` so
   the listeners attach ONLY when authenticated and detach on anonymous.
