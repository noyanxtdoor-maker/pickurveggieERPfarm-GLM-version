# Module Dependency Map

## Purpose

PickUrVeggie ERP V3 is composed of many interconnected modules.

This document defines:

- Which module depends on another
- The source of truth for each type of information
- How data flows between modules
- What happens when a module fails
- How to prevent circular dependencies

The goal is to ensure the ERP behaves as one integrated ecosystem.

---

# Dependency Philosophy

A module may consume information from another module.

However, a module should not own information that belongs to another module.

Example:

Wrong:

Inventory stores employee information.

Correct:

Inventory stores Employee ID and retrieves employee details from HR.

# Dependency Direction Rules

## Rule 1:
Physical events happen first.

Example:

Worker applies fertilizer.

↓

Production record created.

↓

Inventory decreases.

↓

Production cost updates.

↓

Accounting receives the financial impact.

---

## Rule 2:
Accounting receives transactions.

Accounting does not control operational events.

Example:

A worker can record a harvest even if accounting is not currently being reviewed.

---

## Rule 3:
AI advises.

AI does not execute sensitive actions.

Examples of prohibited AI actions:

- Approving payroll
- Deleting records
- Sending money
- Changing accounting history

---

## Rule 4:
Offline data is temporary.

The mobile device is never the master database.

Supabase remains the primary source of truth.

---

# Failure Isolation Strategy

## Internet Failure

Mobile:

Continues offline.

Synchronization occurs later.

---

## AI Service Failure

Codex unavailable.

ERP operations continue normally.

---

## IoT Failure

Sensor monitoring stops.

Farm operations continue using manual observations.

---

## Mobile Device Loss

Device access is revoked.

User account remains.

ERP data remains secure.

---

## Payment Service Failure (Future)

Manual recording can continue.

The ERP should never depend entirely on third-party payment services.

---

# Circular Dependency Prevention

Avoid situations like:

Inventory waits for Accounting.

Accounting waits for Inventory.

Result:

System deadlock.

---

Correct flow:

Physical event

↓

Operational record

↓

Validation

↓

Accounting impact

# Integration Priority Order

> **Superseded for sequencing (Stage A4 · [ODR-004](../28_Enterprise_Architecture_Audit/ODR_004_Implementation_Precedence.md)).** The canonical implementation order is ODR-004 (with `18.05` + `27.03`). ODR-004 **corrects** the legacy list below: the **Financial Foundation (accounting) precedes the operational engines**, and the **inventory ledger precedes production-consumption costing**. The legacy list placed Farm Operations before Inventory and Accounting after HR/Payroll, contradicting this document's own dependency map (audit findings P4-02/P2-02). The list below is retained as historical context; the **dependency map above remains valid** and is the basis from which ODR-004's order is derived.

When building the ERP, modules should be implemented in this order (historical — see ODR-004 for the canonical order):

1. Foundation Database and Security

2. User and Permission System

3. Farm Operations

4. Inventory

5. Purchasing

6. Sales and Delivery

7. Accounting

8. HR and Payroll

9. Mobile Application

10. Codex AI

11. IoT

12. Reporting and Business Intelligence

# Final Dependency Principle

Every module has a responsibility.

No module should duplicate another module's ownership.

Data should flow in one clear direction:

Real-world event

↓

ERP transaction

↓

Business validation

↓

Financial impact

↓

Analysis and intelligence

↓

Human decision

The ERP succeeds when every module knows what it owns and what it only references.
